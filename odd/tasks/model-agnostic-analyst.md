# Model-agnostic analyst narrator

The Inicio analyst prose (`Narrator` port, docs/adr/0013) only had a Claude adapter. Add one
OpenAI-compatible Chat Completions adapter in both backends so any compatible provider works.

## Specs

- S1 — The owner asked: «entonces sipges en la pantalla inicio funciona con claude, quisiera que fuera agnostico al modelo , por ejemplo usar con codex , deepseek y mas ??» and approved the proposal with «perfect confirmo u atorizo tus correciones».
- S2 — Accepted proposal: one adapter speaking `POST {base}/v1/chat/completions` (OpenAI, DeepSeek, Ollama, OpenRouter, Groq, vLLM). Configuration: `SIPGES_ANALYST_PROVIDER=openai-compatible`, `SIPGES_ANALYST_BASE_URL` (required, the API root such as `https://api.deepseek.com`; the adapter appends `/v1/chat/completions` unless the URL already ends in `/v1`, then only `/chat/completions`), `SIPGES_ANALYST_API_KEY` (required unless the base URL is loopback, sent as `Authorization: Bearer`), `SIPGES_ANALYST_MODEL` (required for this provider; ids may contain `A-Z a-z 0-9 . _ : / -`, 1–128 chars, so `deepseek-chat`, `deepseek/deepseek-chat` and `llama3.1:8b` are valid). No new SDK or dependency: `fetch` in TypeScript, `net/http` in Go. Same system prompt, same `<informe>` wrapping, `max_tokens` 4000, one retry and the same 20 s budget as the Claude adapters.
- S3 — Existing behaviour stays: unset or `none` keeps the narrator off; `anthropic` keeps its current validation, default model and adapter unchanged. The provider error becomes exactly `SIPGES_ANALYST_PROVIDER must be unset, 'none', 'anthropic' or 'openai-compatible'`. New errors: `SIPGES_ANALYST_PROVIDER=openai-compatible requires SIPGES_ANALYST_BASE_URL`, `SIPGES_ANALYST_BASE_URL must be https, or http on a loopback host`, `SIPGES_ANALYST_PROVIDER=openai-compatible requires SIPGES_ANALYST_API_KEY`, `SIPGES_ANALYST_PROVIDER=openai-compatible requires SIPGES_ANALYST_MODEL`, `SIPGES_ANALYST_MODEL is not a valid model id`.
- S4 — Privacy and safety (docs/adr/0030): the adapter receives only the `SanitisedPayload` the egress guard already cleared; the guard and its wiring are not changed. Only the configured base URL is contacted: redirects fail the call, proxy variables are ignored (Go). Errors are fixed texts: neither the key, the URL nor the briefing reach a log or an error message. `finish_reason` `length` fails as truncated; an empty or missing message content fails; `content_filter` fails as declined.
- S5 — Citations: reuse whatever the analyst service already does with the narrative's `[n]` markers; if it already rejects markers absent from the briefing, add one test proving the new adapter's output goes through it; if no such check exists, record that in the Log and do not invent one here.
- S6 — Go parity: `apps/api-go` reads the same variables with the same messages and behaviour; `apps/hosting-cloudflare/src/go-routes.ts` forwards `SIPGES_ANALYST_BASE_URL` and `SIPGES_ANALYST_API_KEY` to the Go container like the existing analyst variables.
- S7 — Docs: an addendum in docs/adr/0013 (provider choice, why one OpenAI-compatible adapter instead of an SDK such as Vercel AI SDK or LangChain), and the env tables in docs/integrations/README.md and docs/deployment/local-install*.md. Sending real data to an external provider remains the owner's data-processing decision (odd/tasks/functional-closure.md T5); say so next to the new variables.
