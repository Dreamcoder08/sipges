## Design

T2 decisions, recorded before the code (closure-roadmap T7). Code in `deploy/desktop/updater/`.

- Signature: Ed25519 through `node:crypto`. A release is a local directory holding `package/` (the T1
  builder output), `release.json` (format, version, minimum previous version, platform, architecture,
  the SHA-256 of every file and the target of every internal link) and `release.sig` (base64 Ed25519
  signature of the exact `release.json` bytes). Creating a release writes the signer's public key into
  the package as `update-public-key.pem`, so it is hashed, signed and ships inside the installed version.
  The key that verifies an update is the one inside the currently installed version, never the incoming
  one. Only the very first install or the adoption of a keyless old install takes an operator-supplied
  `--trust-key`. No key: updates stay disabled. Tests generate throwaway keys in a temp directory; no key
  file is committed.
- Release source: a local directory only; no publication is authorised. Version is `metadata.json` of the
  package, which must equal `release.json`; ordering is Semantic Versioning 2.0 precedence.
- Layout: install root with `versions/<version>/` (complete, verified copies; files copied, never
  hardlinked, per L18), `current.json` (the pointer, replaced only by one atomic rename of a fully written
  temp file; no symlinks, so it works on Windows), `install.json` (absolute state folder, written once),
  `update.lock`, `update-journal.json` and `update.log` (JSON lines). The state folder lives outside
  `versions/`; an old install keeps its own state folder where it is.
- Transaction: lock, recover any journal left by a crash, verify signature, version, minimum previous and
  platform, stage into `versions/.staging-*` while hashing the copy, rename into `versions/<version>`,
  take a dated pre-update copy beside the state folder, rehearse on a second copy when the previous
  version was adopted (S5: real data on the laptop), migrate, switch the pointer, readiness. Migration
  failure restores the state folder from the pre-update copy (the failed folder is moved aside, never
  deleted); readiness failure switches the pointer back and restores the state. A crash at any step
  leaves the pointer on a complete version; the journal lets the next run roll back to the previous
  version and restore the state. The updater itself never writes the state folder: only the injected
  migration (in the CLI, the first boot of the new version) does. Code downgrade never pretends to
  reverse a migration: going back always uses the pre-update copy.
- CLI `update.mjs` boots the version's `start.mjs` on a free loopback port for migration and readiness;
  tests inject both functions and never boot a server. Pure Node, no new dependency.
